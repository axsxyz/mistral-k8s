# 8. Intégration continue (GitHub Actions)

## Objectif

Qu'à chaque push, une machine neutre vérifie tout le projet :

- la validité statique : scripts, chart, manifests, Terraform ;
- et qu'il **se déploie vraiment** et répond, de zéro.

## Le workflow : `.github/workflows/ci.yml`

| Job | Étapes |
|---|---|
| **static** | outils installés par `scripts/install-tools.sh` (mêmes versions qu'en local) → `shellcheck` → `helm lint` avec les 3 jeux de values → `kubeconform` (manifests générés, validés contre les schémas Kubernetes 1.37, en mode strict) → `terraform fmt -check` + `validate` → JSON du tableau de bord |
| **e2e** (après static) | cluster kind dans le runner → `terraform plan -out` / `apply` du profil CPU avec `values-ci.yaml` → `curl` de `/v1/models` puis d'une vraie complétion, avec vérification que la réponse n'est pas vide |
| **diagnostics** (en cas d'échec) | `get all`, `describe pods`, événements, logs du serveur |

**Ce que j'ai testé en local avant de pousser :**

```
kubeconform : Valid: 3, Invalid: 0 (× 3 profils) ; Valid: 5 (k8s/manual + bench/job)
terraform fmt -check : ok
shellcheck : ok (une info SC1091 corrigée)
```

## Les choix

- **Pas de GPU sur les runners GitHub gratuits.** La CI déploie donc le **profil CPU**. C'est exactement la raison
  d'être de ce profil : le même chart, les mêmes probes, le même Service, testés de bout en bout.
- **`values-ci.yaml`.** Un runner public a 4 vCPU (moins pour un repo privé), dont une partie est déjà réservée par le
  control plane kind. La request de 4 CPU du profil local laisserait le pod `Pending` jusqu'au timeout de Terraform.
  En CI : 1 CPU, 2 threads, contexte de 2 048.
- **Mêmes outils qu'en local.** La CI appelle `install-tools.sh`. Pas de « ça marche chez moi » : les versions et les
  checksums sont les mêmes partout.
- **Diagnostics automatiques.** On ne peut pas se connecter à un runner pour déboguer : tout ce qu'il faut est imprimé
  en cas d'échec.
- **`concurrency` + `cancel-in-progress`.** Un nouveau push annule le run précédent de la même branche.
- **`permissions: contents: read`.** Le jeton du workflow n'a que le droit de lire le code (principe du moindre
  privilège).

## Concepts

- **CI (intégration continue).** Chaque changement est vérifié automatiquement, au plus tôt, dans un environnement
  propre et reproductible.
- **Validation statique et test de bout en bout.**
  - La validation statique attrape les erreurs de syntaxe et de schéma en quelques secondes.
  - Le test de bout en bout prouve que l'ensemble fonctionne vraiment, mais en minutes. On fait les deux, le rapide
    d'abord (`needs: static`).
- **kubeconform.** Il valide les manifests contre le schéma JSON de l'API Kubernetes d'une version donnée. Il attrape
  les champs mal orthographiés ou mal placés avant que le cluster ne les refuse.

## Questions d'entretien

- **Comment tester un chart Helm en CI ?**
  `helm lint`, puis `helm template` + kubeconform (validation de schéma), puis un vrai `install` sur un cluster
  éphémère (kind), avec une vérification fonctionnelle.
- **Comment tester un déploiement GPU en CI ?**
  Avec des runners GPU (auto-hébergés, ou les runners GPU payants de GitHub). Sinon, séparer : le profil CPU teste le
  packaging, et un test GPU nocturne ou manuel tourne sur un runner GPU.
- **Où mettre les secrets en CI (un token Hugging Face pour un modèle restreint) ?**
  Dans les *secrets* GitHub, injectés en variables d'environnement, jamais affichés dans les logs. En Kubernetes, un
  objet `Secret`, alimenté par un gestionnaire de secrets en production.
